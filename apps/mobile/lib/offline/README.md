# Offline queue — P0-MOB-05

The **level-agnostic** offline-first scaffold required by PLAN.md Appendix A
(_"Flutter · offline-first (drift/SQLite + sync queue)"_). Writes made while the
device may be offline are captured as `SyncOperation`s, appended to a durable
`SyncQueue`, and later replayed against the generated API client (`lib/api/**`).

## What is here (level-agnostic — safe to build in Phase 0)

| File | Role |
| --- | --- |
| `sync_operation.dart` | Immutable model of one queued write (idempotency key, endpoint, method, payload, UTC `createdAt`, status, attempt count). |
| `sync_queue.dart` | The `SyncQueue` contract: store / order (FIFO) / transition pending writes. No policy. |
| `in_memory_sync_queue.dart` | Reference `SyncQueue` implementation. Pins the semantics and is unit-tested without native SQLite. |
| `local_db.dart` | drift/SQLite `SyncQueue` (`DriftSyncQueue` + `SyncQueueItems` table). The durable production store. |
| `sync_queue_store.dart` | Platform-conditional **opener** for that store — i.e. the `QueryExecutor` choice. `_io` = drift `NativeDatabase` over a real file; `_web` = null (B-289). Kept out of the barrel, like `local_db.dart`. |
| `sync_processor.dart` | The **level-dependent** drain policy. Level (a) "queue-and-replay" is implemented here (B-242, answered). |

## The level question (answered)

Offline level **(a)** vs **(b)** was **Open Question #5 (PLAN.md §11)**. Wei
answered it — **BLOCKERS.md B-242 = level (a) "queue-and-replay"** — and that
policy lives in `sync_processor.dart`: FIFO by `createdAt` · 2xx removes · 4xx
dead-letters and continues · 5xx/transport defers and stops · one drain at a time.
Nothing else in this package holds policy.

## Codegen

`local_db.g.dart` is generated by `drift_dev` via `build_runner`
(`dart run build_runner build`) and is never hand-edited.

## Where the queue and the processor live (B-262)

`AppServices` owns both:

* **the queue** — `bootstrap()` calls `openDurableSyncQueue()`, so the store is
  drift/SQLite wherever the platform can open one and a queued write survives an
  app kill. It falls back to `InMemorySyncQueue` (honestly non-durable, writes
  replay only within the session) when the platform has no executor — today that
  is the **web build**, whose drift `WasmDatabase` needs `sqlite3.wasm` +
  `drift_worker.js` assets this repo does not vendor → **BLOCKERS.md B-289**.
* **one `QueueDrainProcessor`** — `AppServices.syncProcessor`. The three
  offline-write screens (`pm_checkin`, `pm_notes`, `pm_checklist`) take that
  instance instead of building their own, and `SyncResumeDrain`
  (`lib/app/sync_resume_drain.dart`) drains it on mount and on app resume. Before
  this, the only processor was constructed inside a screen's `build`, so a queued
  op drained only while that screen was mounted — and the re-entrancy guard, being
  per-instance, was rebuilt (and reset) on every rebuild.

None of that changes the drain policy above.

## Testing

The queue contract is verified against `InMemorySyncQueue`
(`test/offline/sync_queue_test.dart`) so no native SQLite library is needed for it.
`DriftSyncQueue` is exercised for real in `test/offline/sync_queue_store_test.dart`:
the production `openSyncQueueAt` over a real on-disk SQLite file, closed and
reopened to simulate an app kill. The wiring is covered by
`test/app/app_services_queue_test.dart` and `test/app/sync_resume_drain_test.dart`.
