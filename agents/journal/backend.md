### 2026-07-27 · orch-A · P2-BE-58 gate-4.5 round-1 FAIL → FIXED (commit b0b0500)
- gate-4.5 round-1 FAILED and was RIGHT — a critical, real bug. The B-149 guard on the 7 **updateThroughChain** callers (po/wo approve+reject · subcon inspect pass+reject · **subcon approve-payment**) was NON-ATOMIC. Root cause: updateThroughChain does TWO round-trips — a non-locking selectThrough SELECT (my status predicate was applied HERE, in the `where`) then a SEPARATE `UPDATE ... WHERE id IN (ids)` with the status ABSENT. Under READ COMMITTED true concurrency, the loser's UPDATE blocks on the winner's row lock, then PostgreSQL EvalPlanQual re-checks the loser's qual — only `id IN (ids)` — against the committed row; id is unchanged → still matches → the loser commits a DUPLICATE (a second ap_billing on approve-payment = double payment, no unique index to catch it).
- My round-1 "live concurrency proof" (6× Promise.all inject → 1×200/5×409) was a FALSE POSITIVE — that result is what SERIALIZED execution produces (the handlers didn't actually overlap at the SELECT), so it only exercised the sequential/idempotent path, never the concurrent window. gate-4.5 flagged exactly this.
- FIX (b0b0500): added an optional `guard?: SQL` param to updateThroughChain — a predicate on the target table's OWN columns re-applied to the FINAL UPDATE (`.where(and(inArray(id, ids), guard))`). The 7 callers now pass the status pre-state as `guard`; the resolve `where` keeps the status too (fast-path early-exit). Now the loser's EPQ re-check includes `AND status=<pre>` → 0 rows → 409 / StaleStateError rollback. The other 7 B-149 sites (direct db.update / updateThrough — which folds `where` into the real UPDATE) were ALREADY atomic; untouched.
- RE-VERIFY: 983 api · tsc/db clean · **DETERMINISTIC RACE PROOF** that provably hits the concurrent window: a raw pg conn `BEGIN; SELECT … FOR UPDATE` locks the passed period; the handler (fired, not awaited) inserts ap_billing then BLOCKS on its guarded flip; the raw conn then `UPDATE …='paid'; COMMIT` (the concurrent winner) and releases the lock; the handler's UPDATE unblocks → EPQ re-matches `id AND status='passed'` vs the committed 'paid' row → 0 rows → 409, ap_billing UNCHANGED (tx rolled back · NO double payment), status=paid. This deterministically distinguishes the fix from the bug (the old code would have committed a 2nd ap_billing).
- LESSON (round-1): a guard that composes a resolve-then-update door is only atomic if the pre-state is on the FINAL locking UPDATE, not a prior non-locking SELECT — and a concurrency proof must PROVABLY overlap the critical section (a raw FOR UPDATE lock forcing the window beats Promise.all, which can silently serialize). Never retire a money guard on a proof that can't reach the concurrent case.
